# Hosting the backend on Render

How to run the Express backend in [`backend/`](../backend) (auth, incidents, help requests, responder
matching, simulator, Socket.IO) on [Render](https://render.com), using the Blueprint in
[`render.yaml`](../render.yaml).

The Next.js dashboard and Express API run as two connected free Render services. The dashboard links to the
role-based rescue console and checks its health; the rescue console links back to statewide intelligence.

| Part | What | Time |
| --- | --- | --- |
| 1 | Understand the free tier | 3 min |
| 2 | Create the service from the Blueprint | 15 min |
| 3 | Check it works | 10 min |
| 4 | Optional: keep data, real data providers, stay awake | — |
| 5 | Troubleshooting | — |

## Part 1: What you're getting (and the free-tier limits)

`render.yaml` creates two **web services**, `rescuermap-rset` and `rescuermap-dashboard-rset`:

| Setting | Value | Why |
| --- | --- | --- |
| Root directory | `backend` | The backend has its own `package.json` |
| Node | 24.14.1 (`NODE_VERSION`) | `backend/package.json` requires Node 24 |
| Build | `npm ci && npm run build` | Clean install, compile TypeScript to `dist/` |
| Start | `node dist/src/cli/seed-if-empty.js && node dist/src/server.js` | Seed demo accounts only into an empty database, then start |
| Health check | `/api/health` | Render waits for this before switching traffic |
| `JWT_SECRET` | generated by Render | Random 256-bit secret, never in git |
| `TRUST_PROXY` | `1` | Render sits in front of the app; rate limits need the real client IP |
| `PROVIDER_MODE` | `mock` | Built-in simulated data; no API keys needed |
| Plan / region | Free / Singapore | Change in `render.yaml` if you want |

**Free-tier behaviour you must plan around:**

- **It sleeps.** After 15 minutes without traffic the service spins down. The next request wakes it, which
  takes about a minute. Open the URL a couple of minutes before a demo (or see Part 4C).
- **The database resets.** The backend stores data in SQLite on the service's local disk, and a free service's
  disk is wiped on every redeploy, restart and wake-up. Each fresh start re-seeds the demo accounts and demo
  incident, so it always *works*, but anything created during a session can disappear. For a hackathon demo
  that's usually fine; for keeping data see Part 4A.
- Free-instance allowance and sleep behavior are controlled by Render's current account policy. Both services
  are explicitly configured with `plan: free`; check the Render dashboard before adding any paid resource.

## Part 2: Create the service

### 2.1 Render account and repository access

1. Sign up at <https://dashboard.render.com/register>, ideally **with GitHub**.
2. Render needs access to the `amith-m-s/Rekshakan` repository. When Render asks you to connect GitHub, grant
   access to that repository.
   - If you can't see it, the repository owner (`amith-m-s`) must either install the **Render GitHub app** on
     their account for this repo, or create the Render service from their own Render account and invite you to
     the workspace. (The same situation as the Vercel project.)

### 2.2 Pick the branch

The Blueprint and two small backend changes it relies on (`seed-if-empty` and `TRUST_PROXY`) are on
**`feature/dashboard-supabase`** until the pull request is merged.

- **PR not merged yet:** use branch `feature/dashboard-supabase`.
- **PR merged:** use `main`.

If you deploy `main` before the merge, the start command fails with
`Cannot find module '.../dist/src/cli/seed-if-empty.js'`.

### 2.3 Create the Blueprint

1. In the Render dashboard: **New → Blueprint**.
2. Select the **Rekshakan** repository and the **branch** from 2.2.
3. Blueprint path: leave as `render.yaml`.
4. Render reads the file and shows **1 service: rescuermap-backend**. It asks for the one variable marked for
   input:

   **`CORS_ORIGINS`**: the browser origins allowed to call the API, comma-separated, **no spaces, no trailing
   slashes**. For example:
   ```
   https://rescuermap.vercel.app,http://localhost:3000,http://localhost:5173
   ```
   - Include each frontend URL that will call this backend from a **browser**.
   - The phone app (React Native) and PowerShell/curl don't send an `Origin`, so they're always allowed.
   - The backend's own test console (served from the same service) doesn't need to be listed.
5. Click **Apply** (or **Deploy Blueprint**). Render creates the service and starts the first build.

### 2.4 Watch the first deploy

Open **rescuermap-backend → Events / Logs**. A healthy first deploy shows, in order:

1. `npm ci` installs packages (including building `better-sqlite3`).
2. `> tsc` compiles with no errors.
3. `Seed complete: …` (first start on a fresh disk).
4. A JSON log line with `"server_started"`.
5. The deploy is marked **Live**.

The service URL is shown at the top, e.g. `https://rescuermap-backend.onrender.com`
(Render adds a suffix if the name is taken).

## Part 3: Check it works

Replace `$u` with your service URL. Use PowerShell.

```powershell
$u = "https://rescuermap-backend.onrender.com"

# 1. Health (may take ~1 minute if the service was asleep)
Invoke-RestMethod "$u/api/health"

# 2. Log in as the demo coordinator (all demo accounts use password Demo123!)
$login = Invoke-RestMethod "$u/api/auth/login" -Method Post -ContentType application/json `
  -Body '{"email":"coordinator@rescuermap.local","password":"Demo123!"}'
$login.data | Select-Object -ExcludeProperty accessToken
$token = $login.data.accessToken

# 3. An authenticated call
Invoke-RestMethod "$u/api/incidents" -Headers @{ Authorization = "Bearer $token" }
```

Then in a browser:

- `https://<service>/` → the backend's **test console** (log in with a demo account).
- `https://<service>/docs` → interactive **API documentation**.

Demo accounts (all `Demo123!`): `admin@`, `coordinator@`, `resident@`, `responder@` + `rescuermap.local`.

> These accounts and password are public (they're in the repo). Anyone who finds the URL can log in. Fine for
> a demo; don't store anything real.

**Socket.IO** works on Render. Connect clients to the service URL (`wss://` is handled automatically) with
`{ auth: { token } }`, as described in `backend/README.md`.

## Part 4: Optional upgrades

### 4A. Keep data between restarts (paid)

Persistent disks need a paid instance type.

1. In `render.yaml`, change `plan: free` to `plan: starter`, and add under the service:
   ```yaml
       disk:
         name: data
         mountPath: /var/data
         sizeGB: 1
   ```
   and add an environment variable:
   ```yaml
         - key: DATABASE_PATH
           value: /var/data/rescuermap.db
   ```
2. Commit, push, and in Render → **Blueprints → your Blueprint → Manual Sync** (or let auto-sync apply it).
3. `seed-if-empty` sees the existing users on later starts and leaves your data alone.

A service with a disk can't scale beyond one instance, which is how this SQLite backend is designed anyway.

### 4B. Use real data providers

The default `PROVIDER_MODE=mock` uses built-in simulated data. To use the real NASA FIRMS / Open-Meteo / OSRM /
Nominatim / Groq adapters:

1. Render → **rescuermap-backend → Environment → Add Environment Variable**:
   - `PROVIDER_MODE` = `real`
   - `NASA_API_KEY` = your FIRMS map key
   - `GROQ_API_KEY` = your Groq key (a separate key from the dashboard's is fine)
2. **Save, rebuild, and deploy.**

Values edited in the dashboard stay unless the Blueprint later sets the same key.

### 4C. Avoid the cold start during a demo

- Open `https://<service>/api/health` 2–3 minutes before presenting.
- Or add a free uptime monitor (e.g. UptimeRobot) that requests `/api/health` every 10 minutes during the event.
  This keeps it awake but uses instance hours continuously (one service running all month fits in 750 hours).

### 4D. Change settings later

`render.yaml` is the source of truth for build/start commands, plan and non-secret variables. Edit it, push,
and Render syncs the Blueprint (auto-deploy is on for new commits). Secrets entered in the dashboard
(`CORS_ORIGINS`, keys) are kept.

## Part 5: Troubleshooting

| Symptom (in Render logs) | Cause | Fix |
| --- | --- | --- |
| `Cannot find module '…/dist/src/cli/seed-if-empty.js'` | Deploying a branch without the Render changes | Use `feature/dashboard-supabase`, or merge the PR first (2.2) |
| Build uses Node 20/22; `engines` or `better-sqlite3` errors | `NODE_VERSION` missing | Environment → `NODE_VERSION` = `24.14.1`; **Manual Deploy → Clear build cache & deploy** |
| `was compiled against a different Node.js version` (`NODE_MODULE_VERSION`) | Stale build cache from another Node version | **Manual Deploy → Clear build cache & deploy** |
| `tsc: not found` / TypeScript missing | `NODE_ENV=production` set, so dev dependencies were skipped | Remove `NODE_ENV` from Environment; redeploy |
| Deploy stuck, then "health check failed" | App crashed on start | Read the log lines just before; usually one of the above |
| Browser console: `Origin not allowed` / CORS error | Frontend URL not in `CORS_ORIGINS` | Add the exact origin (scheme + host, no trailing slash); save; redeploy |
| `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR` warnings | `TRUST_PROXY` missing | Set `TRUST_PROXY=1` |
| Everyone gets `429` at once | Same as above: all clients seen as one IP | Set `TRUST_PROXY=1` |
| First request takes ~1 minute | Free service was asleep | Expected; see 4C |
| Data created earlier is gone | Free disk reset on restart/redeploy/sleep | Expected on free; see 4A |
| Login fails with correct demo password | Seeding failed on start | Check logs for `Seed complete` / `Seed skipped`; redeploy |
